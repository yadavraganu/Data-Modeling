## 1. Dimensional Surrogate Key

A **Surrogate Key** is a system-generated, sequential integer (or UUID) used as the **Primary Key** of a dimension table. It has absolutely no inherent business meaning.

* **Purpose:** It uniquely identifies a specific row in a dimension table and acts as the join target for fact tables.
* **Why use it?** It insulates the data warehouse from changes in the source system, allows you to handle **Slowly Changing Dimensions (SCD Type 2)** by giving historical versions of the same entity their own unique rows, and offers better join performance (joining on integers is much faster than strings).
* **Example:** `CustomerSK = 48291`

## 2. Dimensional Natural Key

A **Natural Key** (sometimes called a Business Key) is the original identifier assigned to an asset or entity by the operational source system.

* **Purpose:** It identifies the actual real-world entity across systems.
* **Why use it?** You need it to map incoming source data to your data warehouse dimension. While a surrogate key changes if a customer updates their address (in SCD Type 2), the natural key remains exactly the same because they are still the same human being.
* **Example:** An employee ID (`EMP-10042`), a vehicle VIN, or a Social Security Number.

## 3. Dimensional Durable Supernatural Key

A **Durable Supernatural Key** (or Durable Business Key) is a single, unchanging surrogate key assigned to a unique business entity, and it **never changes**, even if that entity's natural key changes in the source system.

* **Purpose:** To permanently tie all historical versions of an entity together.
* **Why use it?** If a company gets acquired and their customer ID (Natural Key) changes from `OLD-123` to `NEW-999`, your standard SCD Type 2 tracking might break or treat them as two different people. A *Supernatural Key* is generated by the data warehouse to say: "Regardless of what the source system calls this entity today, yesterday, or tomorrow, this is Entity #55."
* **Example:** | CustomerSK (Surrogate) | CustomerNK (Natural) | DurableSK (Supernatural) | Version |
| :--- | :--- | :--- | :--- |
| 101 | OLD-123 | **9999** | 1 |
| 102 | NEW-888 | **9999** | 2 (System migration) |

## 4. Degenerate Dimension Key

A **Degenerate Dimension Key** occurs when a dimensional attribute (usually a transaction control number like an invoice or order number) lives directly inside a **Fact table** without having a corresponding dimension table of its own.

While these are typically stored as raw operational Natural Keys, Kimball dictates specific scenarios where you **must evaluate and assign a surrogate key** to a degenerate dimension:

* **Purpose:** To identify transactional identifiers directly within the fact table while protecting against messy source system data constraints.
* **Why use a Surrogate Key here?**
1. **Non-uniqueness / Key Reuse:** If the control numbers overlap across different physical locations (e.g., two POS terminals assigning the same invoice number) or if the source system wraps back to zero and reuses numbers over time.
2. **Storage Optimization:** If the original transaction control number is a bulky alphanumeric column (like a 24-byte string), substituting it with a lean integer surrogate key directly in the fact table saves massive storage and memory footprint.
3. **BI Tool Capabilities:** If business users need to drill across on the transaction number and the BI tool requires a physical relationship, a surrogate key is assigned (though, as Kimball notes, creating that associated dimension table means it is technically no longer degenerate).


* **Example:** A `FactSales` table containing `Quantity`, `Amount`, and a system-generated integer `Transaction_SK` that resolves a messy, overlapping source ticket number.

## 5. Date Dimension Surrogate Key

A **Date Dimension Surrogate Key** is the primary key of your dedicated Date dimension table, but unlike standard surrogate keys, it is typically formatted as a **smart key** (an integer in the format `YYYYMMDD`).

* **Purpose:** To connect fact table rows to a robust `DimDate` table containing attributes like Fiscal Quarter, Day of Week, Holiday Flag, etc.
* **Why use it?**
1. Standardizing dates into an integer (e.g., `20260709` for July 9, 2026) makes partitioning fact tables incredibly efficient.
2. It bypasses the need to generate sequential database sequences for dates.
3. It easily handles "Unknown" or "Not Applicable" dates using specific smart keys like `19000101` or `-1`.

### Summary Comparison

| Key Type | Where it Lives | Format | Changes Over Time? |
| --- | --- | --- | --- |
| **Surrogate Key** | Dimension (PK) & Fact (FK) | Sequential Int / UUID | **Yes** (New row per history change) |
| **Natural Key** | Dimension | String / Int (from Source) | **Rarely** (But can happen) |
| **Durable Supernatural Key** | Dimension | Int / UUID | **Never** |
| **Degenerate Key** | Fact Table Only | String or Evaluated Surrogate Int | **Never** (Tied to transaction) |
| **Date Surrogate Key** | DimDate (PK) & Fact (FK) | Smart Int (`YYYYMMDD`) | **Never** |
